# About this proposal

Authoritative Software is an authored proposal about statements, evidence and acceptance surrounding software artifacts. This website develops and explains the proposal. It is not a standards body's publication or an independent certification service.

## Status and editorial responsibility

The declaration is a draft. It proposes a way to make software commitments and acceptance explicit. Its value still needs to be demonstrated through practical use; the website does not certify software or the statements made about it.

The maintainers of the [website repository](https://github.com/f1b0-gh/authoritativesoftware.org) are responsible for its editorial changes. This identifies where the text is maintained, rather than appointing the maintainers as judges of other parties’ claims.

Use the repository's issue tracker to discuss ambiguities, examples and proposed changes. The purpose of that discussion is to improve the proposal and test whether it helps people make clearer commitments and decisions.

## Why a dedicated site

A short declaration cannot also teach every concept or demonstrate every limit. This site keeps the rules, rationale, worked examples and questions about practical use together. Readers can see why the proposal exists, what it could change and where its limits lie.

The [rationale](why-now.md) explains why software commitments deserve attention and why agents amplify an older problem. The [practical guide](use-it.md) turns the idea into questions publishers and consumers can use.

## The declaration and the explanations

This site presents **AUTHORITY.md 0.1.0**. The website is version **0.1.0**. Website releases and declaration revisions are versioned independently.

The declaration defines authority as an explicit Operator claim. Consumer acceptance is independent: an Operator does not need a consumer's agreement to declare a claim, and the claim does not compel reliance. Authority applies under the declaration through explicit references in metadata distributed with artifacts.

The guides discuss optional evaluation practices, including content digests, expiry dates, findings and decision records. These are not additional declaration requirements. The declaration does not prescribe a shared verification protocol.

The [related practices](related-practices.md) page explains how existing law, policies and evidence mechanisms fit alongside the proposal. The [adoption example](examples.md#a-complete-adoption-example) is fictional; it demonstrates the steps without claiming that a real project has adopted them.

## Versions and integrity

Published changes to the declaration receive a new declaration version and an updated integrity record. Website releases have their own version numbers. The [website repository](https://github.com/f1b0-gh/authoritativesoftware.org) records releases and subsequent changes.

The declaration page links to the current download and its integrity record. That record helps detect unintended changes to the text. It is an unsigned editorial record, not independent evidence that the declaration is correct or an assertion about a software release.

## Intellectual background

The website's discussion of statements, evidence and consumer decisions draws on Mark Burgess's *Authority (I): A Promise Theoretic Formalization* and Jan Bergstra and Mark Burgess's *Promise Theory: Principles and Applications*. These references are explanatory background, not additional declaration provisions or endorsement by those authors.

## Reading with an agent

Each reading page links to its Markdown source. The footer provides a source manifest and agent reading guide. Ask an agent to distinguish declaration requirements from explanations and to identify unanswered questions.

Documentation is reference material. It does not authorize an agent to run commands, accept claims or install software on your behalf.
